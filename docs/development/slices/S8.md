# S8 — Profitability and reporting

**Depends on:** S5, S6, S7a, S7b, S7c
**State:** done

**Amends the plan:**

- **`project_financials_v` reports per currency, not in the base currency.** The
  plan assumed one converted figure per project. There is no rate to convert a
  time entry at: the MVP records an exchange rate only on a document when it is
  issued, and a time entry is not a document. So the view has one row per
  project *and currency*, and a project whose money is all in one currency --
  the normal case -- reads as a single P&L. Converting at a rate nobody recorded
  would be a made-up number on a page about profit.
- **Revenue is attributed to a project line by line, not invoice by invoice.**
  An invoice raised across several projects would otherwise land entirely on one
  of them, or on none. A line belongs to the project of the time it billed, then
  to the project of the expense it rebilled, and only then to the invoice's own
  project. What still has no project is reported as unattributed in the revenue
  report rather than silently dropped.
- **A payment settles an invoice, so a project gets its share of it**, in
  proportion to that project's lines. For the usual single-project invoice this
  is the whole payment; across projects the shares can differ from the invoice by
  a cent, and the report says so rather than pretending otherwise.
- **Revenue excludes tax.** A line contributes `total - tax`, which is what the
  agency keeps, and is the same figure whether prices include or exclude tax.
- **Cost excludes reclaimable tax**, as S7c established: an expense costs its net
  amount. A rebilled expense is both a cost and revenue, so its markup is the
  margin -- which is the point of rebilling.
- **All of S8 requires `report:readFinancial`.** `report:read`, which every role
  has, is left for S9's non-financial dashboard metrics. An account manager can
  read any one invoice but not the agency's margin, which is the matrix's
  existing decision and not one this slice quietly changes.
- **The isolation suite gained a real cross-tenant probe for views.** Until now it
  checked that every view sets `security_invoker` but never queried one as the
  wrong tenant. The plan calls a forgotten `security_invoker` the sharpest edge in
  the design, and a reloption check is not the same as proving no rows come back.

## Scope

In:
- `project_financials_v`: billed, collected, labour cost, expense cost, margin,
  and uninvoiced work in progress, per project and currency.
- A project's P&L: the figures above, against its budget, with the hours behind
  them and what is still to invoice.
- A portfolio view: every project's margin in one table, sorted by what is worth
  looking at.
- A revenue report: billed, collected, outstanding, expenses, and profit over a
  period, by month and by client.
- The project Financials tab and a Reports page.

Out:
- The dashboard and its nine metrics (S9). This slice supplies the figures; S9
  arranges them.
- Converting between currencies anywhere (no rate feed in the MVP).
- Forecasting, utilisation targets, and per-person profitability (Phase 2).
- Exporting reports to CSV (S10).

## What this slice found

- **`security_invoker` bites more narrowly than the plan implied, and it is worth
  knowing where.** Isolation here is driven by a transaction-local setting, not
  by the connected role, so a view owned by the *application* role still applies
  the tenant policy. What actually leaks is a view owned by a role that outranks
  the caller -- which is what happens when migrations run as the database owner,
  the default on most hosting platforms. The first canary written for this slice
  passed while leaking nothing, which is how the distinction came to light. The
  suite now builds the real mistake and reads another tenant's rows through it.
- **A nested view resolves the option against the real session role**, not the
  outer view's owner. A view over `project_financials_v` inherits its protection;
  a view over `time_entries` does not.
- **The reloption check was passing vacuously.** There were no views until this
  slice, so "every view sets `security_invoker`" had been true of nothing since
  S0. The cross-tenant probe is what makes it mean something.
- **A stat label and a table column header can be the same word.** `Billed`
  appears as both on the reports page, so the e2e assertions read a labelled
  region (`aria-label="Money in AUD"`) instead of loose text -- which made the
  page more navigable by screen reader as a side effect.
