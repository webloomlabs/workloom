# S9 — Dashboard

**Depends on:** S3, S5, S7a–c, S8
**State:** done

**Amends the plan:**

- **One procedure, nine independent queries.** The plan says "one query per
  card", which is about not building a nine-way join, not about nine HTTP
  endpoints. `dashboard.get` fans out in parallel and returns a section per
  card; a card the caller has no permission for is never queried and comes back
  null. One round trip, one permission story, and each number still has its own
  query.
- **Money is shown in the base currency, from the rates already recorded.** The
  plan asked for a base-currency dashboard and S8 established that nothing is
  converted at a rate nobody wrote down. Both hold here: invoices, expenses, and
  payments each carry a `*_base_minor` captured when they were written, so the
  money cards are exact for a single-currency installation and use those stored
  rates otherwise.
- **Estimated profit says what it could not count.** Labour is the one cost with
  no base-currency figure -- a time entry is not a document and has no recorded
  rate -- so profit counts time logged in the base currency and reports the hours
  it had to leave out. The spec calls the metric "estimated"; this is the part
  that makes it so.
- **The sales pipeline is per currency**, for the same reason: a deal records a
  value and a currency and never an exchange rate. The base currency comes first.
- **"Recent activity" is the audit log**, not the CRM activity feed. On a
  dashboard the useful question is what happened across the agency -- an invoice
  sent, a payment recorded, a project completed -- and that is what the audit log
  already records. It follows `auditLog:read`, so a developer sees the rest of
  the dashboard without it.
- **The dashboard is the home page.** `app/page.tsx` redirected by role as a
  placeholder; it is replaced by `app/(app)/page.tsx`, which inherits the
  application chrome.
- **Every card compares against the previous period.** A revenue figure with
  nothing to compare it to is a number, not information. Current and previous
  come from one query each, not two.

## Scope

In:
- The nine metrics of spec §6.1: revenue, outstanding invoices, expenses,
  estimated profit, active projects, open tasks, upcoming deadlines, leads, and
  the sales pipeline — plus recent activity.
- A period selector (this month, quarter, year), in the organization's time
  zone, with the previous equivalent period for comparison.
- Cards that appear only where the viewer's role can see them, so the same page
  serves a developer and a finance lead.

Out:
- Configuring which cards appear, and in what order (spec §6.1 defers it).
- Charts. The figures and their comparisons are the slice; drawing them is not.
- Any new aggregate that is not one of the metrics named above.
- CSV export of the dashboard (S10).

## What this slice found

- **A `created_at` default is not the pinned clock.** The suite fixes "today" so
  that date boundaries are testable, but a lead's `created_at` comes from the
  database's own `now()`, so the leads card fell outside its own window whenever
  the suite happened to run late in the day. The fixture now dates those rows
  explicitly. Anything a service does not stamp with `ctx.now` needs the same
  treatment.
- **"Active projects" cannot be compared against last month.** It is a position,
  not a flow, and answering "how many were live then" needs history the schema
  does not keep. The first attempt produced a plausible-looking number that
  double-counted; it was replaced with no comparison at all, and "completed in
  the period" -- which is a flow -- carries the comparison instead.
- **Card labels collide with navigation labels.** "Pipeline", "Leads" and
  "Expenses" name both a card and a nav link, so the browser tests read cards
  inside a labelled region rather than anywhere on the page. That made the page
  more navigable by screen reader as a side effect, as the same problem did in S8.
- **Replacing the placeholder home page broke two older specs** that asserted
  signing in lands on `/pipeline`. It now lands on the dashboard, which is the
  point; both were updated rather than worked around.
- **Duplicate workers are an operational trap, twice now.** An old worker left
  running from an earlier session lacks `WORKLOOM_ALLOW_PRIVATE_WEBHOOKS` and
  steals webhook deliveries from the one started for the test run, which looks
  exactly like a broken dispatcher. Check for exactly one worker before blaming
  the code.

## Notes for later slices

- **S10's export** should reuse `dashboard.get`: it already returns every figure
  the page shows, per period.
- **Streaming the cards** with Suspense would let a slow section render late
  rather than hold the page. The procedure already returns them independently, so
  this is a transport change, not a domain one.
